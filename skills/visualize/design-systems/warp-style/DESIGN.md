# Warp Style

_Independent reference inspired by Warp's public product and documentation surfaces. Not affiliated with or endorsed by Warp._

## §1 Canonical Canvas

Warp style is a warm dark agentic development environment born from the terminal. The current product story includes Warp Terminal, Warp Agent, Oz cloud agent orchestration, local and cloud agents, open-source development, multi-model support, Warp Drive, task lists, permissions, profiles, MCP, and shared team context. The brand should feel like a terminal evolved into a controlled agent workspace.

Use warm charcoal, off-white type, Inter, DM Mono, low-radius controls, terminal panes, agent sessions, task lists, command outputs, file diffs, permissions, and session observability. Do not add neon gradients or cyberpunk chrome. The product is powerful because it stays visible and controlled.

### global-header

Use a quiet dark header: Warp, Product, Oz, Agent, Docs, Blog, Pricing, Enterprise, Download, Contact Sales. Keep nav understated and readable.

### agentic-dev-hero

Hero copy should say the product is an open agentic development environment born from the terminal. Pair copy with a terminal plus agent orchestration screenshot, not an abstract AI graphic.

### terminal-session-panel

Terminal panels show command blocks, outputs, prompts, working directory, git state, exit status, and block boundaries. The block model is part of Warp's identity.

### universal-input-card

Universal Input cards show terminal mode and agent mode in one input. Include natural language prompt, command suggestion, context chips, and keyboard shortcut.

### agent-mode-card

Agent Mode cards show a developer prompt, agent reasoning steps, commands to run, output, correction loop, and final result. The user remains in control.

### warp-agent-card

Warp Agent cards show codebase indexing, model choice, tool permissions, diffs, tests, and multi-step plan. Keep it practical, not magical.

### oz-orchestration-card

Oz cards show cloud agents, queues, active sessions, logs, review state, and ability to join a session. This is agent infrastructure for teams.

### cloud-agent-workforce

Cloud workforce panels show multiple agents, repo, task, status, branch, PR, tests, and owner. Use table density and live status.

### local-agent-card

Local agent cards show commands running in the user's environment, approval gates, secrets boundaries, and file context. Local control is a key trust point.

### multi-model-card

Multi-model cards show model provider, harness, task fit, token/cost state, and routing. Avoid model-logo wallpaper; show why the model was selected.

### permission-profile-card

Permission cards show profiles, autonomy level, always ask, allow, deny, production limits, command categories, and environment risk.

### task-list-card

Task lists break complex work into steps. Show planned, running, blocked, done, and needs review states. The list should feel editable by the developer.

### context-attachment-card

Context cards show attached files, folders, blocks, docs, symbols, workflows, and environment variables. Make context visible and removable.

### warp-drive-card

Warp Drive stores workflows, notebooks, prompts, and environment variables for personal or team use. Use a library layout with shared/private state.

### workflow-card

Workflow cards show reusable command sequences, parameters, description, owner, and run action. This is terminal automation as a product primitive.

### notebook-card

Notebook cards combine prose, commands, outputs, and saved context. Keep them developer-readable and not document-heavy.

### mcp-card

MCP cards show connected tools, server status, scopes, available commands, and agent usage. Keep integration permissions clear.

### code-diff-card

Diff cards show file path, additions, removals, test result, and review action. Use restrained diff colors on the warm dark canvas.

### review-session-card

Review cards show agent session summary, commands run, files changed, tests, risks, and approve/continue controls. This is where trust is earned.

### open-source-card

Open-source cards show repo, license, contributors, issues, pull requests, sponsor, and roadmap. Warp's open workflow should feel visible and participatory.

### team-admin-card

Admin cards show seats, teams, permissions, shared Drive objects, audit, billing, and policy controls. Keep enterprise controls calm.

### pricing-plan-card

Pricing cards show individual, team, and enterprise plans with AI usage, agents, collaboration, Warp Drive objects, admin controls, and support.

### download-platform-card

Download cards show macOS, Windows, Linux, shell integrations, version, and install command. Keep them utilitarian.

### docs-layout

Docs pages use left nav, article, copy buttons, right TOC, OS tabs, and Markdown export. Warp docs are part product UI, part manual.

### changelog-card

Changelog cards show release, platform, feature, date, and docs link. Use tight rows.

### footer-directory

Footer groups Product, Agent, Oz, Docs, Community, GitHub, Pricing, Security, and Company links. Keep it dark and quiet.

## §2 Palette

Warp's palette is warm charcoal, off-white, muted tan-gray, and subtle elevated dark. It is intentionally anti-neon.

#### warm-charcoal

Use warm near-charcoal as the page floor. It should feel brown/graphite, not pure black.

#### off-white

Use off-white for foreground and primary buttons. It should look softer than stark white.

#### warm-muted

Use warm muted text for secondary copy, command metadata, timestamps, and inactive states.

#### terminal-surface

Use slightly lifted dark surfaces for panes, blocks, and admin cards. Borders are subtle and warm.

## §3 Typography

Warp typography is plain and developer-readable.

#### inter-display

Use Inter for display with medium-light weight and tight tracking. Avoid hard techno type.

#### mono-code

Use DM Mono or similar for commands, prompts, paths, logs, and code.

#### serif-accent

Instrument Serif can appear rarely for editorial emphasis, but never inside product controls.

## §4 Composition Rules

Warp compositions should show agent work as visible, inspectable terminal activity.

### terminal-first

Start from terminal panes, commands, blocks, diffs, and outputs. The terminal is the origin.

### control-visible

Show approvals, permissions, autonomy level, and command visibility when agents act.

### context-visible

Show the files, blocks, docs, workflows, or MCP tools attached to an agent task.

### session-not-chat

Agent interaction is a session with commands and outputs, not a consumer chat bubble stack.

### warm-restraint

Use texture through typography, borders, and warm neutrals. Avoid glows and gradients.

## §5 Accessibility And States

Dark developer surfaces must keep tiny code and status text readable.

### focus-state

Use off-white focus rings with enough offset on warm dark surfaces.

### permission-state

Permission states use labels: always ask, allowed, denied, prod mode, local only, cloud allowed.

### agent-state

Agent states use queued, planning, running, waiting approval, failed, reviewing, complete.

### command-state

Command states show exit code, duration, stdout/stderr distinction, and retry action.

## §6 Anti-Patterns

Warp style fails when it becomes generic AI terminal neon.

### avoid-neon-terminal

Do not use green-on-black hacker nostalgia or cyberpunk glow.

### avoid-chatbot-layout

Agents must be grounded in commands, files, context, and diffs.

### avoid-hidden-autonomy

Never hide what the agent can do or what permissions it has.

### avoid-over-rounded-saas

Controls are tight and practical. Big pill SaaS buttons are wrong for Warp.
