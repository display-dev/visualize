# Creation procedure (default `/visualize <topic-or-path>`)

Before following the instructions below, apply the shared rules in SKILL.md.

The default invocation creates a new artifact. The agent picks a template across all 35 in `templates/`, composes against the resolved context and tokens from SKILL.md, and writes self-contained HTML.

Autonomous harnesses (Codex-class) have been observed jumping to file writes before the user confirms direction. Gates below prevent that.

## Preflight

Before composing, confirm:

1. **Context loaded.** Resolve artifact context, brand/context source, token source, and fallback behavior per SKILL.md before choosing a template or writing code. If fallback context is used because `DESIGN.md` / `PRODUCT.md` are absent, extract binding brand cues from project instructions: named fonts, palette roles, logo/mark rules, density/register, and anti-references. If those instructions cite token files, stylesheets, design guidelines, or logo components, read those files before composing. Do not treat those cues as optional mood. **Brand-source precedence when sources disagree:** persisted `DESIGN.md` and `tokens.css` win for visual tokens (colors, fonts, surfaces); `PRODUCT.md` wins for voice and audience; fallback project instructions fill gaps but do not override persisted brand tokens unless the user explicitly says so in the current request.
2. **Brand-fidelity lock.** From the cues resolved in step 1, record the applicable invariants across the categories below. These are enforceable, not aspirational. Do not invent invariants where the brand profile is silent — absence is a valid answer for any individual category.
   - **Named fonts.** If the brand profile or fallback source names specific fonts, those fonts must lead the body / heading / code CSS stacks in the artifact. `system-ui`, `Inter`, `-apple-system`, or any other generic sans cannot lead the stack unless the brand explicitly names them.
   - **Named palette / color system.** If the brand profile names palette roles or uses a specific color system (OKLCH, `color-mix`, `lab`, `lch`), `--background` / `--foreground` / `--primary` / borders / surfaces must derive from that palette and use that color system, not from fallback cream-paper, generic grays, or seed-generated hues.
   - **Named anti-references.** If the brand profile names specific aesthetics to avoid, the first viewport cannot instantiate them under another label.

   These invariants (whichever apply) are re-audited at pre-render time in build step 7. If any invariant is violated in authored CSS, revise before rendering — do not surface the artifact to the user.
3. **Product clear.** Topic understood: what's the artifact for, who reads it, when.
4. **Artifact mode picked.** Choose the composition mode from the reader job before selecting a template:
   - `document` — evidence-heavy prose, strategy, research, reviews, briefs, sourced analysis, decisions, and tradeoffs. Default here when the reader needs to understand an argument.
   - `canvas` — spatial synthesis where relationships, flows, maps, topology, or workshop framing are the main read.
   - `dashboard` — repeated/status metrics where monitoring, comparison, exceptions, or operational scanning are the main read.
   - `deck` — slide or presentation sequence where each screen is consumed separately.

   Mode describes consumption, not aesthetic register. A `document` can still use product-native, application-like, spatial, editorial, or technical-drawing grammar when that grammar expresses the source and brand. Do not let the conservative mode default choose the artifact's look for you.
5. **Template picked.** Select from `templates/*/template.md` using template name, description, Use when, and Do not use when. Templates are starting points, not fixed artifact shells: customize the chosen template to fit the reader job and source, then fall back to pattern recipes for recurring structures the template does not cover. Template names are weak evidence; required structure and reader job are strong evidence. Pick the most specific template only when its required structure fits the source without inventing missing fields. If a named template would force a time axis, live-status semantics, escalation path, operational checks, slide sequence, scoring model, or other content the source does not provide, choose the broader document template and borrow only bounded primitives. Bounded primitives are small structures inside the chosen mode — e.g. labeled time-window rows, status marks, compact scenario tables, one contained topology figure — not the named template's full chrome or layout system. State the choice with one-line rationale.
6. **Composition reflex check.** Before sketching shape, name up to three artifact-class defaults you must NOT assume — at least one when an obvious reflex exists for the class. The defaults are moves that appear across every AI-generated version of this artifact class regardless of source or brand — the median answer to the class's prompt.

   The reflex defaults for any artifact class tend to cluster around the dominant masthead pattern, the default section rhythm, the default verdict/answer placement, and the default secondary-navigation device (TOC, sidebar, sticky chrome). Identify the ones that apply to the class at hand (up to three).

   For each default named, cite the brand, source, or reader-job evidence that justifies an alternative shape — "the source doesn't make comparison claims, so no head-to-head primitive; replace with the source's strongest framing claim as the lede" is valid. "I want it to feel different" is not — that's novelty-for-its-own-sake.

   Output stays internal to preflight; the shape gate carries forward only the chosen alternatives, not the rejection process. If you cannot name even one obvious reflex default, the artifact class isn't class-saturated enough for this check — say so and skip.
7. **Shape sketched.** What sections appear, derived from the source's structure and framing claims, and what source-required primitives (table for comparison, chart for measured data, code for snippets, diagram for relationships prose cannot carry) does each section need. If a section needs a chart, sparkline, KPI tile, or quantitative table that visualizes measured data, also load [data-viz.md](data-viz.md) before composing. If a figure is likely to be a relationship diagram, load [diagram.md](diagram.md) plus the tentative non-spatial type reference routed directly from `SKILL.md` before proposing the shape. Ordinary comparison/evidence tables use the table pattern recipe instead.
8. **Mutation check.** If a target path was given, confirm whether overwriting or writing fresh.

Mode defaults are intentionally conservative. Phrases like "make it visual", "make it beautiful", "polish this", or "design this" do not by themselves justify `canvas`, `dashboard`, or `deck`. They still require a reader job that needs spatial synthesis, operational scanning, or presentation pacing. For `document` mode, visual craft comes from a visible argument: typography, rhythm, evidence structure, spatial grouping, tables, diagrams, contrast, and pacing. A document should still feel designed. Restraint is a tool, not the goal; do not let document mode collapse into a lightly styled memo.

`document` mode defaults to an unboxed reading surface. Use boxes, cards, large radius, and display-scale type only when they clarify a real content role: repeated entities, independent state, comparison, alerting, or a deliberate cover moment. Do not use them to make ordinary sections, metadata, source lists, summaries, rules, lifecycle steps, or takeaways feel "designed." Brand tokens supply character; artifact mode decides scale.

Document context belongs in the reading flow. Dates, confidence, source paths, audience, owner, and other frontmatter should sit near the title/thesis as labeled rows, compact definition lists, or quiet inline context within the same reading measure. Do not promote metadata into a right rail, split-cover column, or standalone facts panel unless the artifact is explicitly a reference directory where the metadata itself is the main object. A TOC rail is different: it can help a long document, but it should not compete with the opening argument or make the first desktop view read like an application shell.

Document prose stays prose. Do not promote full-sentence or paragraph-length claims into bold display blocks; that turns the reading hierarchy into a battle card. If a claim needs emphasis, use a short heading, a normal-weight lead sentence, or a labeled callout whose body remains body-weight. Bold belongs to phrase-level emphasis, row keys, states, totals, and focal values, not whole explanatory paragraphs.

## Shape gate

Halt before any code edit. Present a shape-inventory message to the user and wait for explicit approval before proceeding. The gate is the instruction to wait, not the banner shape.

Render the message as ordinary markdown (bullets, bold) — never as a fenced code block. Tone is conversational; lead with the proposal, not with a banner. Don't print "STOP" or any other all-caps self-instruction as user-facing copy.

Required content in the message:

- **Mode:** document, canvas, dashboard, or deck + one sentence explaining the reader job.
- **Template:** picked template name + a one-line rationale for the pick.
- **Sections:** the section list, in the order they'll be composed, derived directly from the source's structure and framing claims — not from artifact-class convention.
- **Source-specific reading choice:** the one reading-order or composition choice the source itself motivates — e.g. "lead with the comparison table because the source is explicitly a comparison brief" or "open with the verdict because the source is explicitly advisory." If the source doesn't motivate a distinguishing reading choice, "default linear argument because the source is linear" is a valid answer — restraint paired with a source fact about the source's shape. Do not invent a distinguishing choice to satisfy this field. This is not "what makes this artifact distinctive"; it's "what reading choice the source requires."
- **Organizing idea:** how the composition itself makes the subject easier to understand. Name the relationship, contrast, sequence, decision, or object from the source that shapes the opening, section rhythm, or explanatory primitive. If the source has no useful organizing idea, say so and use a restrained reading experience instead of manufacturing one. This field is about the artifact's visual argument, not a decorative motif.
- **Visual system:** define the artifact's type role, color roles, surface roles, rhythm/variation rule, and how the source-specific reading choice and organizing idea are visually carried. Color roles must describe jobs, not swatches: thesis/verdict, metadata/navigation, evidence/comparison, risk/state, source/provenance, focal emphasis. Expressiveness may come from composition, type, density, spatial rhythm, imagery, interaction, or color; a restrained palette is valid when another dimension carries the point of view.
- **Primitives (only when a section requires one):** for each section that *requires* a primitive beyond prose (table for comparison, chart for measured data, code for a snippet, diagram for a relationship prose cannot carry), name the primitive and the section it serves. Sections that don't require a primitive stay as prose. There is no upfront primitive budget — primitives follow the sections that need them.
- **Relationship figures (only when present):** state the outer artifact shell independently from each figure. For every figure, name the source-backed entities and relationships, semantic pattern, routed type, direction and primary reading path, group/boundary meaning, complexity budget, desktop and mobile topology (including any split or redraw), and whether geometry is authored directly or calculated locally before inline-SVG normalization.
- **Mobile shape:** how the first two phone screens read. Name what compresses, collapses, or disappears so desktop chrome doesn't become mobile clutter. If the header carries metadata, propose labeled fields rather than rounded chips, and keep them in the same reading flow as the title/thesis.
- **Brand:** one-line readout from the brand-fidelity lock (preflight step 2) — applicable font / palette-or-color-system / anti-reference invariants, or explicitly note none specified for a category. Don't enumerate token paths, CSS variable names, or hue values in the gate; if the user asks, expand on request.
- **Composition reflex consequence (only if preflight step 6 surfaced reflexes):** one sentence per chosen alternative — e.g. "avoiding the research-report masthead; opening leads with the strongest source claim." If preflight step 6 was skipped because the artifact class isn't class-saturated, omit this field. Do not surface the rejection process itself, only the chosen consequences.
- A single-sentence approval prompt at the end ("Sound right, or change something first?", "Want me to proceed?", etc. — vary it).

If the proposed shape is `document` mode, viewport-scale heroes, metadata rails, facts columns, cards, or metric strips must earn their place by carrying the source-specific reading choice or a real reader task. They are not banned; they fail only when they are generic chrome, fake quantification, or competing metadata. Bars, score widgets, KPI tiles, radar charts, lane maps, and market maps require supplied evidence plus a reader job that needs that primitive. "Visual interest" is not a rationale.

`shape=pass` only counts when the user separately approves the brief or supplies a pre-confirmed one. Self-authored briefs (the agent paraphrasing its own preflight and proceeding) do NOT count as approval. "The implementation will be semantic anyway" doesn't skip the gate.

## Build (only after shape=pass)

1. Read the selected template's `template.md`.
2. If the template frontmatter declares `shell: <slug>`, read `shells/<slug>/README.md`. Read shell runtime files only when the artifact needs to inline or modify the mechanics.
3. Decide which pattern recipes are relevant from the user ask and template Creation guidance. Read only those `patterns/<slug>.md` files. Recipes are optional creation guidance, not automatic dependencies.
4. Compose a self-contained HTML artifact from the template contract, selected pattern recipes, brand tokens, and shell mechanics if present. Generated artifacts must not include comments or metadata naming the selected template, recipes, or shell; required runtime markup such as `<slide-canvas>` is allowed.
5. Inline the resolved design tokens into the artifact's `<style>` per SKILL.md. All three selector blocks travel together: `:root` (light), `[data-theme="dark"]` (explicit-dark), and `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]):not([data-theme="dark"]) }` (raw-HTML OS-dark path). See `reference/teach.md` § What goes into DESIGN.md for the token contract.
6. Apply remaining resolved context fields (logo, voice in copy, exceptions whitelist).
7. **Pre-render brand-fidelity audit.** Inspect authored CSS against the brand-fidelity lock from preflight step 2. If the resolved brand font is absent from body / heading / code stacks (or is preceded by a generic font), revise before rendering. If `--background` / `--foreground` / `--primary` / borders / surfaces match fallback values instead of resolved brand tokens, revise. If the artifact's color system uses hex when the brand profile declared OKLCH or `color-mix`, revise. If card elevation pairs a 1px border with a large fuzzy shadow (large blur, low opacity, on the same surface) without explicit justification recorded in the shape gate's visual system, revise — matching SKILL.md's existing Codex-specific rule rather than broadening it. This audit fires whether the brand profile came from `DESIGN.md`, from project-instruction fallback, or from declared anti-references. Generic fallbacks such as Inter, cream editorial paper, or seed-generated hues are wrong when the repo already named a font, palette role, or anti-reference. Brand-invariant violations are not surfaced to the user — revise and re-audit silently.
8. Check the authored CSS against the approved visual system before rendering. Each non-neutral color must map to a repeated semantic role from the shape gate, and the first viewport must use composition, color, surface, type, density, imagery, interaction, or layout to carry the source-specific reading choice and organizing idea. Do not add hues or decoration merely to satisfy an expressiveness check; revise only when the opening has no expressive dimension.
9. Render or inspect the desktop opening and narrow-phone state before calling the artifact done. The desktop opening should read as one document flow: brand/context, title, thesis, and labeled metadata should not become competing columns. The first two phone screens should look intentionally composed, not like the desktop layout stacked: no hero scale that crowds out the thesis, no rounded metadata chip row that becomes noise, no doubled horizontal rules between the header and contents/TOC, no free-wrapping TOC links that read like scattered words, no TOC that consumes the first screen unless navigation is the artifact's main job. Header metadata should use explicit labels (`Updated`, `Input`, `Audience`, `Owner`, `Source`) so context survives scanning.
10. **Specificity revision pass.** Read the composed artifact back. First name the strongest quality of the rendered first viewport. If the honest answer is only "clean," "polished," "on-brand," or "easy to read," the composition is unfinished: revise until its strongest quality describes what this specific artifact helps the reader see. Then ask: *"Is this the artifact I would produce if I had no special instructions and was asked for a generic <artifact class>?"* If the answer is yes, revise at least one first-viewport structural choice — opening order, section rhythm, primitive placement, metadata treatment, or color/type role — then name the changed structural choice and the source/brand/reader-job evidence behind it. The pass is not satisfied by naming a change in prose; the artifact has to move. If the answer is no, name what specifically makes this artifact distinct from the generic default — the answer must cite source, brand, or reader-job evidence, not "I picked an unusual color." Novelty alone is not the goal; the goal is to surface unintentional convergence toward the median for this artifact class and route the artifact back to the brand profile and source-of-truth.
11. Verify the source-specific reading choice survived the build. It must be visible in the rendered first viewport or first major section, and it must shape the page structure. If the output still reads as a generic clean document with the same content inserted, revise before running the detector.
12. If the artifact contains a data table, inspect the table type roles before running the detector: caption/intro stays `0.8125rem`-`0.9375rem`, header labels stay small uppercase or small-caps, body cells are regular `0.875rem`-`1rem`, first-column row labels are at most semibold, and mono is limited to code/IDs/timestamps/numeric columns.
13. Run `detect.mjs --mode <document|canvas|dashboard|deck>` on the result.
14. If the artifact contains any `figure[data-visualize-diagram]`, run `browser-diagram.mjs --strict` (both explicit themes are the default). The checker blocks and reports non-allowlisted external network requests. Capture desktop and 390 px screenshots, and inspect topology, label legibility, clipping, overlap, crossings, mobile preservation, and the absence of diagram-related external requests. Treat static `diagram/*` errors and browser errors as delivery blockers. Make targeted edits in the same artifact and repeat the static check, browser check, and screenshots. Stop after at most two automatic correction rounds and surface any remaining findings; do not create numbered variants. A later user-requested iteration starts a new, user-directed round.
15. Surface the file path, the desktop/mobile screenshot evidence for a diagram-bearing artifact, and a one-line summary of findings.

Non-diagram detector output remains non-blocking at this stage. Diagram delivery errors follow the bounded repair gate above. Iteration commands (`polish`, `simplify`, `bolder`, `quieter`, `animate`, `review`) handle later refinement.
